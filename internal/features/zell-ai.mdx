## Overview

Zell AI is the assistant experience inside the platform. It helps users ask questions, inspect application data, and work through AI-assisted workflows.

## Scorecard Creation

Scorecard creation is a review-and-confirm workflow, not a one-step write:

<Steps>
  <Step title="Gather and summarize scope">
    Zell AI establishes the workspace, language, call type, scorecard purpose, and approved criteria, then shows the proposed scorecard structure to the user.
  </Step>

  <Step title="Confirm before generation">
    The user must confirm the proposal in a prior turn. Only that confirmation authorizes Zell AI to call `create_scorecard`; asking for analysis or optimization does not.
  </Step>

  <Step title="Generate a reviewable draft">
    Zell AI generates `scorecardData` and passes it to the scorecard form. The generated structured output must include at least one scoring signal. Customer-supplied categories are passed as one complete verbatim criteria block and become one signal per category in the same order.
  </Step>

  <Step title="Review and explicitly save">
    The user reviews the complete generated draft, including signal count, order, names, language, descriptions, guidelines, rubrics, methods, weights, call type, and workspace. Saving is a separate explicit action; generating the draft does not persist or activate it.
  </Step>
</Steps>

<Warning>
Confirmation to generate a draft is not confirmation to save it. Never describe a generated scorecard as created, updated, saved, or live until the separate save action succeeds.
</Warning>

The backend validates generated scorecard output with a stricter schema than persisted scorecard metadata, so a model response with an empty signal list is rejected instead of creating a scorecard that cannot score calls. The Anthropic structured-output schema conversion must unwrap defaulted arrays so `signals` is exposed to the model as an array with `minItems`, not as a generic string field.

For the real-call field flow and the distinction between Evaluation Criteria and User Guidelines, see [Scorecards & Signals](/internal/features/scorecards-and-signals).

## Course Drafts

`create_course` is available to admins and internal-tool admins. The assistant gathers the brief, output language, and module outline, then asks for approval before generation. It reuses approval already in the conversation for an approved brief or an explicitly requested revision. The latest explicit language request takes priority; a target country does not select the output language, and approved module titles stay as agreed.

A successful tool result returns `courseData` for review. It does not save or publish the course. A chat outline is only a proposal. For the user workflow, see [Set Up a Course](/guides/courses).

### Replies and completion status

When course routing is active, the agent requires a tool response and buffers model narration. `create_course` generates a draft; `course_reply` handles discussion and status without an additional verification model call. A missing tool response or exhausted tool loop returns a failure message instead of treating model text as evidence of generation.

For `course_reply` with `kind=status`, the server ignores the model's message and reports either no prior draft or the earlier draft's title and language. When an earlier draft exists, it explicitly states that no new draft was generated in that reply and that saving or publishing has not been verified. Questions, proposals, and informational answers still contain model-written text, and choosing the correct reply kind depends on the model. This protocol does not guarantee that every misleading claim is prevented.

### Draft history and edited messages

The send-message response's `courseData` comes only from the current agent result. An older draft can remain in conversation history without being returned as newly generated data on a later discussion or failed-generation turn.

Prior draft evidence is read from the latest retained assistant message with valid draft metadata. Editing a message removes that message and all later messages, so drafts in the removed history do not count. Session metadata may still contain an older draft; support should use retained message metadata when checking what the current conversation actually generated.

Large message metadata is stored in private storage through `_metadataRef`. New offloaded course messages also keep `_courseDraft` with the title and language in the database. Older references are hydrated when finding draft evidence, and paginated message responses hydrate full metadata. Missing or invalid downloaded metadata yields no hydrated evidence. A title/language summary alone does not prove the full draft can still be loaded.

Replacing edited messages and writing the replacement user message is one database transaction. Saving the assistant result and updating session metadata is another. Private-storage uploads and cleanup occur outside those transactions.

### Generation failures and tracing

Lesson generation uses a structured `steps` array with nonempty content and exactly the expected step orders. Each module gets two generation attempts; within each attempt, the Anthropic adapter can retry invalid structured output twice. Modules run concurrently and all settle before the content stage reports failure. The pipeline does not retry the whole content stage, so one failing module does not regenerate successful siblings within that run.

For a failed course request, inspect the `tool:create_course` span in the session's Langfuse trace and its child `llm` generations. Pipeline failures and thrown tool errors mark the tool span `ERROR` with a `statusMessage`; model-facing error results also carry `is_error`. LLM observations start before the request and finish on success or failure, so elapsed time includes the request. Exhausted structured-output validation retries include the raw output and available model/token usage; successful observations include available cache usage. Not every response without draft data is an error: confirmation requests and discussion can legitimately return no draft.

## Model Picker Defaults

When the Zell AI chat model list loads, the frontend preselects an Opus model when one is available. This is a frontend picker default only; it does not change the backend model list or the backend-declared default.

The fallback order is:

1. First model from `GET /admin/zell-ai/models` whose id includes `opus`
2. Backend-declared default model from the same response
3. First model returned by `GET /admin/zell-ai/models`

Once a user explicitly picks a model in the Zell AI chat, the frontend does not clobber that choice when model data reloads. Support should treat unexpected initial picker values as a model-list ordering/default issue first, and unexpected changes after selection as a frontend state issue.

Source: `src/hooks/zell-ai/modelSelection.ts`, `src/hooks/zell-ai/useZellAiChat.ts`
