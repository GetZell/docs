## Overview

Users & Teams covers user management, invited users, manager relationships, role assignment, and team-level visibility. It is the foundation for access control, coaching views, assignments, and reporting.

## Full Seats

User Management and the tenant usage surfaces display the backend's `currentSeats`. This is a tenant-wide count, independent of the number of rows currently visible in the user or membership table.

`TenantService.computeCurrentSeats(tenantId)` adds:

- Users whose primary `tenantId` matches, whose `role` is `USER`, and whose `isTestUser` is `false`.
- Invitations for that tenant whose `acceptedAt` is `null` and whose `role` is `USER`.

Admins, team leads, internal-tool admins, assessment candidates, and test users do not contribute to the user portion of this count. Pending regular-user invitations still reserve a seat. The invitation query does not apply an expiry filter. Two admins and one regular non-test user, with no pending regular-user invitations and a limit of five, therefore show **1/5 Full Seats**.

`TenantService.getUserUsage` returns `{ currentSeats, seatsLimit }`; an absent seat limit is returned as `null`. The frontend reads this result rather than counting admins or other rows locally.

## Internal Membership Role Edits

`PATCH /internal-tools/memberships/{membershipId}` accepts a `role` and requires authentication and internal-admin access. `MembershipService.updateRole` updates the membership inside a transaction. It also updates the user's role when both the user ID and the membership tenant match the user's primary tenant.

For a primary-tenant membership, changing `USER` to `ADMIN` removes that non-test user's contribution to full seats; changing `ADMIN` to `USER` adds it. Editing a membership in another tenant updates only that membership: it does not overwrite the primary user's role or change the primary tenant's seat count. Other memberships retain their existing roles.

This synchronization runs when a role edit succeeds. There is no historical backfill of previously inconsistent user and membership roles.

## Usage Refresh

The shared `invalidateTenantUserUsage` helper invalidates both query prefixes after successful mutations:

| Surface | Query key | Request |
| --- | --- | --- |
| Tenant User Management and usage | `['tenant-user-usage', tenantId]` | `GET /tenant/user-usage` |
| Internal tenant settings | `['internal-tenant-user-usage', tenantId]` | `GET /internal-tools/tenants/{tenantId}/user-usage` |

Both queries are enabled only when a tenant ID is available. Active matching queries refetch after invalidation; inactive cached queries become stale for their next use.

| Successful mutation | Refresh trigger |
| --- | --- |
| User role edit | `useUpdateUserRole` |
| Internal membership role edit | `useUpdateMembership` |
| Internal user creation | `useCreateUser` |
| User deletion | `useDeleteUser` |
| Internal test-user toggle | `useToggleTestUser` |

Membership role edits also invalidate `tenantMemberships`, `allTenantUsers`, and `users` so the displayed roles refresh alongside usage. Refreshes update usage data; they do not recalculate or repair roles in the frontend.

## Troubleshooting a Seat Disagreement

Check the backend usage response, pending regular-user invitations, and the user's primary `tenantId`, `role`, and `isTestUser`. A membership table can include users whose primary tenant is elsewhere, so its row count is not a seat count.

If a primary-tenant membership displays Admin while its user record still has `USER`, the disagreement may predate role synchronization. Confirm the intended role before applying a membership role edit through internal tools; that edit synchronizes the matching primary user. A frontend refresh alone does not repair stored role disagreement. Do not use a secondary-tenant role edit to repair a primary-tenant role.
