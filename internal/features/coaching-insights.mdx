## Overview

Coaching Insights supports both the manager-facing dashboard for finding coaching opportunities across reps, signals, calls, and coachable snippets and the current-user coaching workspace for an individual rep's own data. The personal workspace is the default view at `/calls`; the historical calls table is available at `/calls?view=list`. The manager dashboard is used inside the unified team Reports workspace at `/admin/team/reports`:

- Missing or non-`real-calls` `type` uses the persisted report type from localStorage key `reports-report-type`, then defaults to `source=SIMULATION`.
- `type=real-calls` mounts the tab with `source=REAL_CALL` and overrides the stored report type.

Coaching Insights answers four main questions:

- Which reps have the greatest coaching need?
- Which signals are weakest across the selected team?
- Which concrete snippets should a manager review with a rep?
- What coaching opportunities can the current user review for themselves?
- Which personal focus areas and call moments should the current user review next?

## Filters

Coaching Insights combines global report filters with tab-local filters.

| Filter | Where it comes from | Backend behavior |
| --- | --- | --- |
| Date range | Unified Reports global filters | Applies to `Call.startedAt`. Previous-period comparisons are only returned when both `dateFrom` and `dateTo` are present. |
| Source | Unified Reports report type | `REAL_CALL` when `type=real-calls`. Otherwise the UI uses the normalized localStorage value from `reports-report-type`; empty, missing, null, or invalid values default to `SIMULATION`. The selector is managed by `useReportTypeRouting` in `src/components/teamManagement/reports/useReportTypeRouting.ts` and persists constants from `src/components/teamManagement/reports/filterPersistence.ts`. Tenants without the Real Calls feature, except local development, fall back to simulations even when real calls is requested or stored. |
| Groups | Unified Reports global filters | Intersects the selected group members with any selected users. |
| Users | Coaching Insights tab | Restricts overview results to selected users. |
| Scorecards | Coaching Insights tab | Matches either the call agent's scorecard or `call.metadata.scorecardId`. |
| Call Type | Coaching Insights API filter | Accepts comma-separated call type labels in `callTypes`. Real calls match `Call.metadata.callType`; simulations match the label of the `CallType` linked through `Agent.callTypeId`. |
| Call Outcome | Coaching Insights API filter | Accepts comma-separated outcome labels in `callOutcomes` and matches `Call.metadata.callOutcome`. |
| Workspace | Request context | If a workspace context exists, overview is scoped to that workspace's users. |

<Note>
When group and user filters are both active, the backend intersects them. If the intersection is empty, the overview returns empty stats and empty lists.
</Note>

### Manager Filter UI And Persistence

`CoachingInsightsFiltersBar` renders report type, user, scorecard, Call Type, and date in the primary row. Group is under **View more**; Call Outcome is also under **View more**, but only when `source=REAL_CALL`. While collapsed, the button counts selected outcomes and adds one when a group is active.

The Reports workspace persists each report type independently through `FilterGroup`:

| Scope | localStorage key | Coaching Insights fields | Default/merge behavior |
| --- | --- | --- | --- |
| Simulation Reports | `reports-filters` | `selectedUserIds`, `selectedGroupIds`, `selectedScorecardIds`, `selectedCoachingCallTypes`, `headerGroupId`, `activeTab` | Arrays default to `[]`, group defaults to `all`, and the default tab is `coaching-insights`. Stored objects are merged over current defaults, so older values receive new fields. |
| Real Calls Reports | `real-calls-reports-filters` | The same fields plus `selectedCoachingCallOutcomes` | The same defaults apply. List-view `selectedCallTypes` and `selectedCallOutcomes` are separate, so switching views does not leak list filters into Coaching Insights. |

The call-type options come from `useCallTypeOptions` and include global defaults plus tenant custom labels. Call-outcome options come from `useCallOutcomeOptions` with the same global-plus-custom behavior. Clearing a multiselect stores `[]`; `buildCoachingInsightsParams` then omits the parameter. Changing user, scorecard, call type, or outcome clears the selected member while the filtered overview loads; the first member in the new response becomes selected when one exists.

The group selector produces `effectiveGroupIds`: a selected `headerGroupId` takes precedence over legacy `selectedGroupIds`. Groups and users are sent only to the overview. Member detail and snippets are scoped by the selected member's `userId` plus date, source, scorecard, call-type, and call-outcome filters.

### Call Type And Outcome Filter Contract

These are label-based filters, not ID-based filters. They are shared by the admin overview, member-detail, and snippets endpoints and the equivalent current-user endpoints.

| Employee-facing name | Request query parameter | Backend path | Database resolution | Default and empty behavior |
| --- | --- | --- | --- | --- |
| Call Type | `callTypes`, comma-separated exact labels | `parseCoachingInsightsFilters` parses the query; `CoachingInsightsFilterQuerySchema` validates it; `CoachingInsightsService` passes it to the Coaching Insights SQL queries. | For `REAL_CALL`, matches `Call.metadata->>'callType'`. For `SIMULATION`, joins `Call.agentId` to `Agent.callTypeId`, then matches `CallType.label`. | Missing or exactly empty (`callTypes=`) becomes `undefined` and does not filter. There is no backend default selection. |
| Call Outcome | `callOutcomes`, comma-separated exact labels | `parseCoachingInsightsFilters` parses the query; `CoachingInsightsFilterQuerySchema` validates it; `CoachingInsightsService` passes it to the Coaching Insights SQL queries. | Matches `Call.metadata->>'callOutcome'` for both real and simulation calls. | Missing or exactly empty (`callOutcomes=`) becomes `undefined` and does not filter. There is no backend default selection. Calls with null or missing outcome metadata only remain when this filter is absent. |

Both parameters accept standard and tenant-custom labels. The SQL compares the supplied strings directly: matching is case-sensitive, values are not trimmed, and unknown labels return no matching calls rather than a validation error. Multiple labels within one parameter are OR conditions. When call type, call outcome, source, scorecard, date, or user filters are combined, the filter groups are ANDed.

The shared query parser uses a single comma-separated string. Repeated query keys are not supported, whitespace around a comma becomes part of the label, and labels containing commas cannot be represented because the decoded value is split on every comma. A literal `null` is treated as the label `"null"`; it is not the same as omitting the parameter.

The filters apply consistently to overview totals, team/member scores, trends, weak signals, engagement, previous-period comparisons, member detail, and coachable snippets. A simulation call without a linked agent/call type cannot match `callTypes`; a real call without `metadata.callType` cannot match it. Any call without `metadata.callOutcome` cannot match `callOutcomes`.

#### Employee Q&A

**Why can the same Call Type selection find both real calls and simulations?**

The backend resolves the same label against different storage: metadata for real calls and the agent's linked `CallType.label` for simulations. Supplying `source` additionally restricts which branch can contribute.

**Does Call Outcome automatically imply real calls?**

No. The outcome filter checks call metadata for either source. Use `source=REAL_CALL` when only real-call outcomes should count.

**Why does an apparently valid filter return an empty dashboard?**

Confirm the exact label and casing, remove spaces around commas, and verify the field exists on the selected source. Also check the existing tenant, workspace, team-lead subtree, user, group, scorecard, source, and date filters because all applicable scopes are combined.

**Are custom labels checked against the tenant's Call Type or Call Outcome configuration?**

No separate lookup validates request values. Tenant isolation comes from the calls/workspaces in the Coaching Insights query. Simulation call types resolve through the linked `CallType` record; real-call types and all outcomes compare stored metadata strings directly.

## Permissions And Scope

The admin Coaching Insights router requires team-lead or admin access.

| Role behavior | Rule |
| --- | --- |
| Admin | Can query the tenant-scoped data allowed by the provided filters. |
| Team lead | Server-side scope is restricted to the team lead subtree. |
| Team lead overview | Requested users are intersected with the subtree. If no users are requested, the subtree is used. |
| Team lead member detail | Returns an empty member detail when the requested user is outside the subtree. |
| Team lead snippets | Returns `{ snippets: [], nextCursor: null }` when the requested user is outside the subtree. |

All overview-level team aggregates only include regular users with `role = USER` and `isTestUser = false`.

## Current-User Endpoints

The non-admin Coaching Insights router exposes read-only endpoints for the authenticated user's own coaching data.

| Endpoint | Auth | Valid query parameters | Scope behavior |
| --- | --- | --- | --- |
| `GET /coaching-insights/overview` | `requireAuth` | `scorecardIds`, `callTypes`, `callOutcomes`, `dateFrom`, `dateTo`, `source` | Forces `userIds` to the current user. If the request has workspace context, overview data is also scoped to that workspace. |
| `GET /coaching-insights/me` | `requireAuth` | `scorecardIds`, `callTypes`, `callOutcomes`, `dateFrom`, `dateTo`, `source` | Loads member detail for the current user only. No `userId` path or query parameter is accepted. |
| `GET /coaching-insights/me/snippets?signalId={signalId}` | `requireAuth` | `signalId`, `scorecardIds`, `callTypes`, `callOutcomes`, `dateFrom`, `dateTo`, `source`, `cursor`, `limit` | Loads snippets for the current user and uses the current user as the snippet viewer. |

Validation is handled by `UserCoachingInsightsSchema` and `UserCoachingInsightsSnippetsSchema`. `signalId` is required and must be a UUID for `/coaching-insights/me/snippets`; invalid values return a bad request before the service layer runs. The call type and outcome parameters are validated as strings, then split into labels by `parseCoachingInsightsFilters`.

Current-user routes intentionally do not expose `groupIds`, `userIds`, `workspaceIds`, member `userId` path parameters, or coaching-focus mutation endpoints. They share the same overview, member-detail, and snippet response schemas as the admin routes.

The current personal Calls workspace filter controls documented below do not yet expose Call Type or Call Outcome. The API accepts both parameters for current-user calls, so other clients can use them without gaining access to another user's data.

## Score Calculations

### Zell Score

Zell Score is computed from call score and coachability:

```text
zellScore = (10 - callScore) * (coachability / 10)
```

The stored value is rounded to two decimals. A high Zell Score means the call has both low performance and high coachability.

### Coachability

Call coachability is computed from snippet-level coachability, weighted by the score gap:

```text
gap = 10 - snippetScore
coachability = weighted average of snippetCoachability by gap
```

Snippets with a perfect score do not contribute because their score gap is `0`.

### Average Performance

Average performance uses `CallEvaluation.totalScore` from valid calls with non-null total score. The overview stats card computes the displayed team average from the daily trend values and rounds it to one decimal.

### Average Coaching Need

Average coaching need is the average of member-level `avgZellScore` values in the current result set. Each member's value is rounded to two decimals.

## Engagement

Engagement measures whether users read the coachable snippets Zell surfaced.

For the full implementation reference, see [Engagement Score](/internal/features/engagement-score).

| Rule | Behavior |
| --- | --- |
| Eligible snippet | `SnippetEvaluation.score <= 5` and `coachability > 5`. |
| Excluded snippet | Any snippet with a `DISLIKE` vote is excluded. |
| Read snippet | Eligible snippet whose feedback has `readAt` set. |
| Daily cap | At most `10` surfaced snippets per user per day count toward engagement. |
| Score scale | Engagement is displayed on a 0-10 scale. |

The daily cap is timestamp-based and inclusive of both ends:

```text
if dateFrom or dateTo is missing:
  cap = 10
else:
  days = max(1, ceil((dateTo - dateFrom) / 1 day) + 1)
  cap = 10 * days
```

A same-calendar-date range with different start and end times counts as two inclusive endpoints, so it caps at `20`. For example, `2026-06-01T00:00:00Z` to `2026-06-01T23:59:59Z` caps at `20`.

Team engagement sums capped snippet counts per user, then computes:

```text
engagement = round((totalRead / totalSnippets) * 100) / 10
```

That means `10.0` is fully read, `5.0` is half read, and `0.0` means no eligible snippets were read.

## Weak Signals

Weak signals show the lowest-scoring signals across the selected scope.

| Rule | Behavior |
| --- | --- |
| Source | `EvaluationCategory` rows joined to valid scored calls. |
| Required data | `score IS NOT NULL` and `signalId IS NOT NULL`. |
| Minimum sample | The signal must have at least `2` evaluations. |
| Sort order | Lowest average score first. |
| Evaluated count | Count of distinct users evaluated for that signal. |
| Previous score | Returned only when both `dateFrom` and `dateTo` are present. |

The UI displays weak signals as bars on a 0-10 scale. Green starts at `7`, amber at `4`, and red below `4`.

## Member Detail

Selecting a member loads that user's detailed signal breakdown.

| Field | Behavior |
| --- | --- |
| Call count | Count of valid calls with a non-null total score for that user. |
| Signal average | Average `EvaluationCategory.score`, rounded to one decimal. |
| Snippet count | Count of eligible coachable snippets for that signal. |
| Read count | Count of eligible coachable snippets with `readAt` set. |
| Signal order | Lowest average score first. |
| Previous signal score | Same signal over the previous period when a full date range exists. |

Member engagement uses the same snippet score, coachability, dislike, source, date, scorecard, and daily-cap rules as team engagement, but only for the selected user. The member-detail query scopes directly to the selected `userId`; in the normal UI flow that user comes from the overview list, where regular-user and non-test-user filtering has already been applied.

## Coachable Snippets

The snippets modal opens from a member signal card or a personal workspace focus area and loads snippets for one user and one signal.

| Rule | Behavior |
| --- | --- |
| Required user | Admin scope uses the selected member's user ID. User scope uses the authenticated user from the current-user endpoint; the frontend still passes `userId` for shared component props. |
| Required signal | The selected signal ID. |
| Score rule | `SnippetEvaluation.score <= 5`. |
| Coachability rule | `SnippetEvaluation.coachability > 5`. |
| Vote exclusion | Snippets with any `DISLIKE` vote are excluded. |
| Sort order | Highest coachability first, then lowest score. |
| Page size | The frontend requests `5` snippets per page. The request schema accepts `limit` from `1` through `100`; the service default is `5`. |
| Pagination | Keyset cursor ordered by coachability descending, score ascending, then feedback ID ascending. The next page loads when the scroll sentinel approaches the viewport. |
| Hydration | Adds transcript context, replies, viewer vote, reviewer, recording URL, and call metadata. |

Snippets endpoints return an object wrapper, not a bare array:

```json
{
  "snippets": [],
  "nextCursor": null
}
```

This applies to both `GET /admin/coaching-insights/member/{userId}/snippets` and `GET /coaching-insights/me/snippets`. A non-null cursor contains `coachability`, `score`, and `feedbackId` and is serialized as JSON in the next request. For admin requests by a team lead, an out-of-subtree member request returns `{ snippets: [], nextCursor: null }` instead of leaking whether the user has coachable moments. For personal workspace requests, the frontend enables the user endpoint only when a `signalId` is present.

The frontend sorts loaded snippets so snippets with replies appear first. Audio playback is coordinated so only one snippet plays at a time.

For the shared snippet hydration behavior, see [Snippet Selection Logic](/internal/features/backend-snippet-selection).
</Note>

## Coaching Focus

Managers can set one or more focus signals for a rep from the member detail panel.

| Action | Behavior |
| --- | --- |
| Set focus | Stores unique signal IDs on `User.coachingFocus` with `assignedBy` and `assignedAt`. |
| Clear focus | Sets `User.coachingFocus` to database null. |
| Validation | The backend checks that the user and all selected signals belong to the same tenant. |
| UI state | Focused signals show a focus badge in the member detail panel. |
| Downstream use | Feedback Inbox prioritizes snippets that match the rep's coaching focus. |

The backend supports both the current multi-signal format and an older single-signal stored format when reading focus data.

## Previous Period Comparisons

When both `dateFrom` and `dateTo` exist, Coaching Insights compares the selected period to the immediately preceding period with the same duration.

| Current selected period | Previous period |
| --- | --- |
| July 8 to July 15 | July 1 to July 8 |
| Last 14 days | The 14 days before that window |

Previous-period values are used for deltas on:

- average performance,
- average coaching need,
- average engagement,
- weak signal average score,
- member signal average score,
- member engagement.
